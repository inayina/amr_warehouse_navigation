# Interview Talking Points

日期：`2026-05-14`

## 1. 这份文档怎么用

这份提纲面向三类场景：

- 面试官让你“用 1 分钟讲一下这个项目”
- 面试官追问“你在项目里具体负责什么、难点是什么”
- 你需要把项目讲成“物流机器人任务执行与导航验证案例”，而不是纯 ROS 2 技术实验

统一口径：

- 当前主线：AMR 仓储导航 + 最小 Mock WMS 任务执行闭环
- 当前定位：面向物流机器人任务执行、导航验证、测试验收的项目案例
- 当前边界：不是完整 WMS，不是多机器人调度系统，不是生产级后端

## 2. 30 秒版本

可以直接这样讲：

“这个项目原本是一个 ROS 2 Nav2 仿真导航项目，我把它继续收口成了一个物流机器人任务执行与导航验证的最小闭环案例。现在它不仅能做仓储 AMR 的建图和导航，还补上了固定任务点、SQLite Mock WMS、任务创建 / 查询 / 执行 / 状态回写，以及自动化测试和验收文档，适合用来展示机器人任务系统和导航基线怎么做最小集成验证。”

## 3. 1 分钟版本

“这个项目的目标不是做完整 WMS，而是验证物流机器人在仓储场景下，从任务输入到导航执行再到结果回写的最小闭环。我先把 Gazebo、SLAM、Nav2 和 fixed task points 整理成稳定导航基线，然后在不改导航主线的前提下，加了 SQLite Mock WMS、CLI、最小 HTTP API、单条 executor 和顺序 task runner。这样就能模拟上层创建任务，经过 Nav2 ready checks 后发送 `NavigateToPose`，最后再把状态写回任务表。除了功能链路，我还补了 PRD、系统架构图、验收清单、测试报告和录屏指南，所以这个项目更像一个可展示、可验收的物流机器人案例，而不是单纯技术 demo。” 

## 4. 3 分钟结构化讲法

### 4.1 先讲背景

- 我想做的不是纯算法项目，而是一个更接近物流机器人系统集成场景的案例。
- 所以我把重点放在“任务怎么进入系统、怎么接到导航层、怎么验证结果”。

### 4.2 再讲目标

- 验证仓储 AMR 的导航基线是否稳定
- 验证最小任务链路是否能安全接回 Nav2
- 验证整个过程是否有测试和验收证据可追溯

### 4.3 再讲系统结构

- 底层是 Gazebo + Nav2 的 AMR 仿真和导航执行基线
- 中间是 fixed task points、ready gate、`NavigateToPose`
- 上层是 SQLite Mock WMS、CLI、HTTP API、executor 和 task runner
- 旁路是测试、报告、验收清单和演示文档

### 4.4 再讲你做了什么

- 固化导航主线入口和固定任务点入口
- 把任务闭环定义清楚：创建、查询、执行、状态回写
- 控制系统边界，不让任务层反向大改导航基线
- 补自动化测试、运行时报告和项目展示文档

### 4.5 最后讲结果

- 项目已经形成“任务创建 -> 查询 -> 执行 -> 状态回写 -> 文档验收”的最小闭环
- `station_a`、`station_b` 的顺序任务执行已拿到真实 `SUCCEEDED` 记录
- 当前本地 `make test` 最新结果为 `63 passed`
- 项目可以被讲成物流机器人任务执行与导航验证案例

## 5. 面试时最推荐的讲述顺序

1. 先定义项目不是完整 WMS，而是最小闭环验证案例。
2. 再讲系统分层：导航基线、任务入口、执行器、验收证据。
3. 再讲你的核心贡献：把技术实现整理成能讲清楚、能验收、能展示的项目。
4. 最后主动交代边界和风险，反而会显得判断更稳。

## 6. 常见追问与建议回答

### 6.1 为什么不直接做完整 WMS？

建议回答：

“因为这个项目当前阶段的目标是验证机器人任务执行和导航层的最小闭环。如果一开始就把订单、库位、前后端、权限和多机器人调度全混进来，反而会掩盖主线问题，也不利于展示导航和任务执行的真实边界。”

### 6.2 这个项目和普通 Nav2 demo 的区别是什么？

建议回答：

“普通 Nav2 demo 更多是在验证点到点导航本身，这个项目在导航基线之外，又补上了固定任务点、Mock WMS 数据层、任务执行入口、状态回写和验收文档，所以它更接近物流机器人任务执行验证，而不是单条 goal 演示。”

### 6.3 你怎么控制任务层不把导航层改乱？

建议回答：

“我把 `navigation.launch.py`、`config/nav2_params.yaml` 和 `maps/warehouse.yaml` 当成稳定基线，任务层只消费 fixed task points，不反向改导航配置；同时通过 ready gate 控制什么时候允许发 `NavigateToPose`。”

### 6.4 你怎么证明这个项目不是只写了文档？

建议回答：

“一方面有自动化测试覆盖配置、Mock WMS、executor、task runner 和 HTTP API；另一方面有真实运行报告，记录了 fixed task points、task runner 顺序执行和 HTTP API 的现场验证结果，所以不是纯 PPT 项目。”

### 6.5 当前最大的未完成点是什么？

建议回答：

“当前最大的边界不是功能缺失，而是 fresh session 下的 ready gate 波动还需要继续观察。所以我会把它如实表述为最小验证闭环，而不是夸大成生产级调度系统。”

## 7. 按岗位调整讲法

### 项目经理 / 技术产品经理

- 多讲目标、边界、里程碑、验收口径
- 少讲参数细节，多讲“为什么要做最小闭环”
- 强调你把技术项目包装成可展示案例的能力

### 机器人系统集成岗位

- 多讲 fixed task points、ready gate、`NavigateToPose`、状态回写和验证报告
- 强调你如何让上层任务入口和导航基线低耦合集成
- 可以提及 launch、参数、TF、lifecycle、action readiness 的判断过程

## 8. 一句收尾

如果面试官问“你觉得这个项目最能体现你什么能力”，可以这样收尾：

“我觉得这个项目最能体现的是，我不只是把导航跑起来，而是能把机器人系统从任务入口、执行边界到测试验收整理成一个更完整、可沟通、可展示的项目案例。”
